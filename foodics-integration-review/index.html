What this document is, and what it is not

The Foodics integration was built and shipped without a review. This document is that review, done after the fact. It reads every line of the integration and the code around it that the integration touches — the payment engine, the QR scan endpoint, the table sync — and reports what is actually there.

Nothing here is a guess. Every finding names the file and the exact behaviour it describes, and every recommendation is followed by the reason it is being made. Where something is a deliberate trade-off that the original developer documented, this document says so and does not re-litigate it.

Each finding is written three ways: what a guest or a restaurant would experience, what the code actually does, and how it would have been built instead. Read the first column and skip the rest, or read all three — both are valid ways through.

Critical

Money can be taken and not recorded, or a bill can be marked paid by someone who did not pay. Fix before the next restaurant goes live.

High

Wrong numbers in reports, private guest data exposed, or a failure mode that turns into a critical one under load.

Medium

The feature works until an unusual but entirely normal sequence of events happens. Staff notice; nobody loses money.

Low

Wasted work, dead code, misleading documentation. No user impact — but this is the layer that hides the bigger problems.

A note on tone

A long findings list is not a verdict on the developer. The parts of this integration that are hard to get right — encrypted credential storage, a consent step to cover a weak OAuth handshake, defensive handling of a POS API that returns numbers where it promises strings — were all done carefully and are documented in the code. The problems that remain are almost all in one place: the boundary between an outside system that can be slow or wrong, and a payment ledger that must never be either.

The feature

What Foodics does inside Smooth today

Before the findings, the shape of the thing being reviewed — because two of the critical findings only make sense once you know where the boundary sits.

Connect Restaurant installs Smooth from the Foodics marketplace Foodics sends the browser back to Smooth with an authorisation code. Smooth forces a fresh owner login, exchanges the code, shows the business name, and waits for the owner to confirm before the connection goes live.
Map Smooth staff link a Foodics branch to a Smooth branch Then pull every Foodics table across into Smooth, creating a QR code for each one. Renames, restores and new tables are handled on repeat runs.
Scan Guest scans the QR on the table Smooth asks Foodics for the open check on that table, copies it into a Smooth order, and shows the guest the bill — items, discounts, tax, service charge.
Pay Guest pays in the Smooth app Just before charging, Smooth re-reads the check from Foodics so the guest cannot settle a total the kitchen has already changed. Then it takes the payment and frees the table.
Deliberate, and correct

The menu never comes from Foodics

Foodics supplies the bill and nothing else. Menu items always come from Smooth’s own catalogue. That separation is enforced in the code and is the right call — it keeps a POS outage from emptying the menu.

Worth knowing

The connection is read-only

Smooth asks Foodics for only two permissions: read business details, and list orders. It never writes back. See F-12 — this one fact shapes how a restaurant has to work day to day, and the client should decide whether it stays.

Worth knowing

Setup needs Smooth staff

A restaurant can connect Foodics on its own, but branch mapping and table sync are admin-only screens. Until someone at Smooth runs them, a connected restaurant sees nothing. See F-11.

Credit where due

Seven things this integration gets right

These are listed first because they are load-bearing: several of them are the reason the remaining problems are recoverable rather than catastrophic.

Security

POS credentials are properly encrypted

Access and refresh tokens are stored with AES-256-GCM, an authenticated cipher, and are never included in any API response — the status endpoint returns a hand-picked list of safe fields. This is the correct standard, not the common shortcut.

Security

A consent step covers a weak handshake

Foodics’ marketplace install uses one fixed state value, which cannot prove the connection was started by the right person. Rather than pretend otherwise, the developer stores the new credentials inert and requires the owner to see the business name and press Connect. The reasoning is written into the code. That is a mature response to somebody else’s protocol limitation.

Security

A failed connection leaves no live key behind

If the restaurant grants fewer permissions than Smooth needs, the just-issued token is revoked at Foodics before the error is returned. Foodics tokens do not expire on their own, so skipping this would strand a working credential forever.

Correctness

A paid bill can never be un-paid by the POS

When Smooth re-reads a check, the recorded paid amount only ever moves up, never down, and a bill Smooth has fully settled is never reopened. The intent is exactly right — F-03 is about a gap in how that intent is enforced, not about the intent itself.

Correctness

The bill is re-checked at the moment of payment

Smooth does not trust the total it showed the guest thirty seconds ago; it asks Foodics again before charging. This is the single most valuable idea in the integration. F-01 and F-04 are about where that check runs, not whether it should.

Robustness

Foodics’ loose data types are handled deliberately

Foodics returns some identifiers as numbers and some as text. Rather than discover this in production, the developer wrote coercion helpers, documented why they exist, and routed every stored field through them.

Robustness

Error logs are scrubbed before they are written

Failures from the POS are stripped of query strings before logging, so an access token in a URL never lands in a log file. Small, easy to skip, and skipped almost everywhere.

Critical

Three ways this can cost real money

These three share one root cause: the integration treats an outside system that can be slow, wrong or impersonated as if it were part of Smooth’s own database.

F-01 Critical Payments

The card is charged first, and the Foodics check runs afterwards — inside a step that can cancel the whole payment

If the POS closes the check, changes the total, or is simply unreachable in the seconds between the card being charged and Smooth writing the payment down, Smooth throws the payment away. The bank has the guest’s money. Smooth has no record of it, no receipt, no refund, and no alert.

In the restaurant

The guest taps Pay. Their bank app pings. The Smooth screen then says “Bill already settled” or “Bill updated, please review” and sends them back. Their money is gone, the table still shows as owing, and there is nothing in Smooth to point at. The waiter’s only options are to argue or to comp the bill.

The most likely trigger is the most ordinary event in a restaurant: a waiter closes the check on the POS at the same moment the guest pays on their phone.

In the code

Card payments are captured by the gateway before Smooth is told about them — confirmStripePayment refuses to proceed unless the intent already reports succeeded, and the intent is created without capture_method: 'manual', so the funds are taken, not held.

Only then does the payment transaction run, and inside it validateAndRefreshFoodicsOrderBeforePayment can throw GoneException, ConflictException or ServiceUnavailableException. Any of those rolls the whole database transaction back, so no Transaction row is ever written. There is no refund call anywhere in the payments service. The Stripe webhook retry re-runs the identical code and fails identically.

How it would have been built

Verify before you charge, never after. The Foodics re-check belongs in front of the gateway call — at the moment the guest opens the payment screen and again immediately before the intent is confirmed. Once money has moved, the only correct behaviour is to record it.

After capture, a changed or closed check is not an error to abort on; it is an overpayment to reconcile. Write the transaction, mark the order over-settled, and raise it for staff. If aborting is genuinely required, it must be paired with an automatic refund and an alert — silence is the one option that is never acceptable.

F-02 Critical Security

The Foodics webhook accepts any message from anyone, and will record cash payments from it

The endpoint that Foodics notifies is open to the public internet with no signature, no shared secret and no sender check. Anyone who sends it a correctly shaped message can mark a bill as paid in cash, close it, and free the table.

In the restaurant

A bill is shown as settled in cash. It was not. The money is missing from the till, the table is released, and the daily revenue report is wrong — and nothing distinguishes the fake entry from a real one, because Smooth writes it through the same code path that records genuine POS cash.

The same message can also close an open bill outright, so a table that owes money is quietly wiped.

In the code

The handler is marked @Public() and takes the body as unknown. The only check is that business.reference matches a connected restaurant — a Foodics account number, not a secret. There is no HMAC check, no shared header, no IP allow-list, and no verification against the Foodics API.

The body is then trusted end to end: a forged payments entry becomes a real CASH transaction, and because a payment with no method name is classified as cash, the attacker does not even need to name one. A global 60-requests-per-minute throttle limits volume, but one message is enough.

How it would have been built

Treat the webhook body as a rumour, not a fact. The message tells you which order to look at; the order’s true state is then fetched from the Foodics API with the restaurant’s own token before anything is written. That single rule removes the entire class of attack and does not depend on what signing Foodics does or does not offer.

On top of that: authenticate the caller with whatever Foodics provides (signature header or shared secret) or, failing that, a long random path segment plus an IP allow-list; and never let an inbound message be the sole authority for creating a money record.

F-03 Critical Race condition

A second guest scanning the QR can erase a payment that just completed

Two people at one table is the normal case, not the edge case. If one is paying while the other scans the code, the scan can write the paid amount back to what the POS last said — which is zero — and the completed payment disappears from the bill.

In the restaurant

One guest pays 200 AED. Their friend scans the QR at the same moment. The bill still reads 200 AED due. The transaction record exists, but the order says nothing was paid, so the table stays occupied and the guest is asked to pay again.

The window is not milliseconds. Because the payment holds the order open while it waits for a reply from Foodics (see F-04), it is wide enough to hit in ordinary service.

In the code

upsertMirroredOrderFromFoodics reads the order’s current paid, computes max(existing, posPaid) in application memory, then writes the result back. Classic read-then-write: the read happens before the payment commits, the write happens after, and the stale value wins.

The payment path guards itself with SELECT … FOR UPDATE. The QR-scan path takes no lock at all, so the guard protects payments from each other but not from a scan.

How it would have been built

Never compute a money figure in application memory when the database can do it atomically. paid should be raised with a single conditional statement — SET paid = GREATEST(paid, :posPaid) — which is correct under any interleaving and needs no lock.

More broadly, only one piece of code should ever write to a mirrored order. Today three do — the scan, the webhook and the payment — each with its own copy of the merge rule. One writer, taking the same row lock the payment path already takes, removes this and F-07 together.

High

Wrong numbers, exposed data, and a fuse waiting to blow

F-04 High Architecture

A call to Foodics runs in the middle of the database transaction that records the payment

The payment transaction opens, locks the order, then waits on a network request to another company’s servers before it can finish. The database gives that transaction five seconds. Foodics is under no obligation to answer within five seconds — and the code sets no time limit of its own at all.

In the restaurant

On a normal day nobody notices. On a slow-network day, payments start failing after the card has already been charged — which is F-01, now firing routinely instead of rarely. If Foodics is rate-limiting Smooth, the code’s own retry can wait up to thirty seconds inside a five-second budget, so the failure is guaranteed.

While each payment waits, it is holding one of a limited number of database connections. Enough of them at once and every restaurant on the platform slows down, not just the one with the POS problem.

In the code

this.prisma.$transaction(…) is called with no options, so Prisma’s defaults apply: two seconds to acquire, five seconds to complete. Inside it, after SELECT … FOR UPDATE, the code calls out to the Foodics REST API.

The HTTP call has no timeout — Node’s fetch has no default, and none is supplied — so a stalled connection holds the row lock far past the point the transaction has already been abandoned. The retry-on-network-error branch checks err.code === 'ECONNRESET', which never matches, because Node wraps network faults in a TypeError and puts the code on err.cause. That retry has never once fired.

How it would have been built

No network call inside a database transaction. Ever. The sequence is: talk to Foodics, get an answer, then open a short transaction that only touches Smooth’s own tables. Freshness is preserved by re-checking the bill version inside the transaction, not by holding the transaction open while you wait.

Alongside that: an explicit AbortSignal.timeout of a few seconds on every outbound call, a total retry budget smaller than the transaction budget, and a fix to the retry condition so it reads err.cause.code.

F-05 High Privacy

The full raw POS record — including the guest’s details held in Foodics — is returned on a public URL

Smooth stores the complete Foodics payload for each check and then hands the whole thing back on the QR-scan endpoint, which requires no login. Whatever the restaurant has recorded about that guest in the POS goes out with it.

In the restaurant

A guest’s name, phone number and other details the restaurant holds in Foodics can be read by anyone who has the table’s QR link — a previous diner, a photo of the table card, a screenshot in a group chat — for as long as that check is open.

For a UAE hospitality client this is a data-protection exposure, not a technical nit.

In the code

Smooth requests customer among the related records it pulls from Foodics, saves the entire response as foodicsSnapshot, and then builds the guest-facing payload with { ...order } — which carries foodicsSnapshot straight through. No serializer strips it: the app registers only a response-wrapping interceptor and a decimal formatter.

The endpoint is GET /qr-codes/:id/menu, marked @Public().

How it would have been built

Build the response, do not leak it. A guest-facing payload should be assembled field by field from an explicit type, so adding a column to the database can never add a field to a public API. The code already builds a clean display bill — it just spreads the raw record underneath it.

And stop requesting customer from Foodics: it is not used anywhere in the bill display, so the safest version of this data is the version never fetched.

F-06 High Reporting

POS payments are mirrored by guesswork: unknown methods become cash, and mixed settlements vanish

Two separate rules decide what Smooth records when a bill is settled at the register. One is too generous, the other too strict, and between them the revenue report can be both overstated and understated on the same day.

In the restaurant

Too generous: a payment whose method name Smooth cannot read is filed as cash. Gift cards, vouchers, delivery-app settlements, an Arabic method name Smooth does not match — all appear in the cash column.

Too strict: when a table settles partly by card and partly by cash at the register, Smooth records nothing at all. The bill looks unpaid in Smooth even though it is closed in Foodics.

In the code

isFoodicsCashPayment returns true when the method name is empty or missing — a fail-open default on a money classification.

Worse, recordFoodicsPosCashPayments exits early unless every payment on the check looks like cash. The per-payment filter inside the loop already handles mixed bills correctly; the outer gate stops it from ever running in exactly the case it was written for.

The fallback that covers unmatched amounts builds its de-duplication key out of figures that change as more payments arrive, so it is not a stable key and can write the same amount twice.

How it would have been built

Map methods explicitly and fail closed. Keep a real mapping from Foodics payment methods to Smooth’s. Anything unrecognised is recorded as OTHER and flagged for reconciliation — never silently promoted to cash, because cash is the one method nobody can audit later.

Delete the all-or-nothing gate and let the per-payment filter do its job. Key each mirrored payment on the Foodics payment id alone, so the same payment can never be written twice regardless of what else changed.

Where normal-but-unusual sequences break the feature

F-07 Medium Race condition

Two guests scanning at once: one of them silently sees no bill

The first scan of a new check creates the Smooth copy. Two simultaneous first scans both try to create it; one loses, and its error is swallowed by a fallback that then reports that the table has no open bill.

In the restaurant

Two people scan the same table code together. One sees the bill. The other sees an empty screen with no explanation and no way to pay, and the waiter has to be called over.

In the code

upsertMirroredOrderFromFoodics does a read, then a create — not a single database upsert — while foodicsOrderId carries a unique constraint. The loser gets a constraint violation, which the QR route catches and turns into “fall back to a native Smooth order”. For a Foodics table there is no native order, so the answer is null.

How it would have been built

Let the database enforce uniqueness rather than checking for it first. A single upsert keyed on foodicsOrderId makes concurrent scans converge on one row instead of colliding.

Separately, the fallback is too broad: “Foodics is unreachable” and “this table has no open bill” are different answers and should not share a screen. Today a POS outage shows a guest an empty bill, which invites them to place a duplicate order.

F-08 Medium Data integrity

A late or repeated POS message can reopen a closed bill and re-occupy the table

Messages from Foodics are applied in whatever order they arrive, with no check of which one is newer. An “order is open” message that arrives after the “order is closed” message wins.

In the restaurant

A table that was cleared shows as occupied again with a live bill on it. Staff clear it manually and lose confidence in the floor view — which is the whole point of the feature.

In the code

Routing is on the order’s status number only; the event name is logged but never used. The open-order path unconditionally sets the Smooth order back to PENDING, guarded only by whether Smooth itself has fully settled it. Nothing compares the incoming record against the timestamp already stored, and nothing de-duplicates a repeated delivery.

The webhook also performs six separate writes with no transaction around them, so a crash midway leaves the order updated and the table not.

How it would have been built

Every inbound message needs an identity and an age. Record the event id so a repeat is ignored, and compare the payload’s update timestamp against the one stored before applying it — older loses. Terminal states should be sticky: once closed, only a newer record may reopen.

Wrap the whole handler in one transaction, so a table’s state and its bill can never disagree.

F-09 Medium Data integrity

Nothing stops two Smooth accounts from connecting the same Foodics business

The identifier that routes incoming POS messages to a restaurant is not unique in the database, and the lookup takes whichever row it finds first.

In the restaurant

A restaurant with a test account and a live account, or one that re-registers on Smooth, can end up with its orders and cash records landing in the wrong account — unpredictably, because the choice is arbitrary.

In the code

businessReference has no unique constraint and no index. The webhook resolves the restaurant with findFirst and no ordering. Absent an index it is also a full table scan on every incoming message.

How it would have been built

If a value routes money, the database should guarantee it points at one place. A unique index on businessReference turns a silent mis-route into a clear error at connection time: “this Foodics business is already connected to another Smooth account.” That is a message support can act on.

F-10 Medium Operations

Messages Smooth cannot match are answered “received” and dropped forever

If a table has not been synced yet, or a branch is not mapped, the incoming message is logged as a warning and discarded — while telling Foodics it was accepted, so it is never sent again.

In the restaurant

During onboarding, or after someone adds a table in Foodics, bills silently do not appear. Nothing in the panel says why. The only trace is a line in a server log nobody is watching.

In the code

Every unresolved path returns { received: true } with HTTP 200. There is no dead-letter store, no counter, no surfacing anywhere in the admin panel. The connection status fields exist in the database and are only ever written by the table sync.

How it would have been built

Always accept the message; never lose it. Store every inbound message with its resolution status, so an unmapped table becomes a visible queue that drains automatically the moment the mapping is created.

Then surface it: an integration health panel showing last message received, unmatched count, and last error is the difference between a support ticket that takes five minutes and one that takes a day.

F-11 Medium Product

A restaurant can connect Foodics but cannot switch it on

Connecting is self-service. Mapping the branch and importing the tables — the two steps that actually make the feature work — exist only on admin screens.

In the restaurant

The owner installs Smooth from the Foodics marketplace, confirms the connection, sees “Connected” — and nothing happens. No bills at any table. They contact support, and someone at Smooth has to finish the setup by hand. Every new branch and every new table repeats it.

In the code

The merchant-facing controller offers exactly four operations: complete, confirm, status, disconnect. Branch mapping, branch listing and table sync live on the admin controller behind an ADMIN role. The merchant API client in the panel mirrors that — it has no sync method at all.

How it would have been built

The step after “Connected” belongs to whoever pressed Connect. Branch mapping and table sync are merchant-owner operations on merchant-owned data; they should sit in the merchant panel behind the same owner check the connect flow already uses.

Keep the admin screens for support. But a marketplace install that needs a phone call to finish is a marketplace install that will show up as a churn number.

F-12 Medium Product decision

Smooth never tells Foodics that the guest paid

This is a design decision, not a defect — but it is the decision that shapes the restaurant’s day, and it should be an explicit choice rather than an inherited one.

In the restaurant

A guest pays the full bill in Smooth. On the POS, the check is still open. A member of staff has to close it manually, choosing some payment method to close it under. Until they do, the POS believes the table owes money.

End of day, the restaurant reconciles two systems by hand. Every heuristic in F-06 exists to paper over this gap.

In the code

Smooth requests only general.read and orders.list, and the Foodics client has no write methods — only reads plus token management. The integration is read-only by construction, and the code never claims otherwise.

The decision to make

Either close the loop, or make the manual step explicit and supported. If Foodics permits a partner to post a payment against an order, requesting that scope removes the manual close, removes the guesswork in F-06, and makes the two systems agree by construction.

If it does not, the workaround should be designed rather than implied: tell merchants plainly that Smooth payments must be closed on the POS, and give them a daily reconciliation view of Smooth-paid-but-POS-open checks. Note that the documents index currently describes this integration as “two-way”; that line should be corrected either way.

F-13 Medium Deployment

If one environment variable is missing, production quietly talks to the Foodics test system

The Foodics address falls back to the sandbox when unset, and nothing at startup checks that the integration is configured correctly.

In the restaurant

Every real restaurant appears to have no open bills, or shows test data. The failure looks like “the integration is broken” rather than “a setting is missing”, which is the most expensive kind of failure to diagnose.

In the code

The base URL defaults to https://api-sandbox.foodics.com/v5. The client id, secret, encryption key and OAuth state all default to empty strings and are only validated when a merchant tries to connect — not at boot.

How it would have been built

Fail loudly at startup, not quietly at runtime. Validate the integration’s settings when the application boots and refuse to start in production with a sandbox address or an empty secret. A deployment that will not start is a five-minute problem; one that starts and behaves strangely is a five-hour one.

Wasted work and loose ends

None of these affect a guest today. They are listed because they are cheap to fix, and because unnecessary work in a hot path is where tomorrow’s performance incident starts.

The shape of it

One decision explains most of this list

Read the findings together and they stop looking like twenty separate mistakes. The integration was built as though Foodics were another table in Smooth’s database: fetch it inline, trust what it says, write straight through to the ledger. Almost everything above is a consequence of that one framing.

The alternative framing — Foodics is a separate system that can be slow, wrong, out of order, or impersonated — would have produced a different design, and it is the design worth moving towards.

Boundary

Fetch outside, write inside

Every call to Foodics completes before a database transaction opens. Transactions touch Smooth’s tables only, and stay short. This removes F-04, defuses F-01, and stops one restaurant’s POS problems from becoming everyone’s.

Trust

Inbound messages are triggers, not facts

A message says look at this order. The truth then comes from the Foodics API using the restaurant’s own token. This removes F-02 entirely and does not depend on what signing Foodics offers.

Ownership

One writer for a mirrored bill

Today the scan, the webhook and the payment each write the mirror with their own copy of the merge rule. One function, one lock, one place to reason about — that is F-03 and F-07 together.

Ordering

Every update carries an identity and an age

Record the event id, compare the source timestamp, ignore anything older than what is already stored. Distributed systems deliver twice and out of order; a design that assumes otherwise is relying on luck (F-08).

Money

Amounts move in the database, not in memory

Read-modify-write on a money column is a lost payment waiting for traffic. Conditional statements and locks are not optimisations here; they are the correctness argument (F-03).

Visibility

An integration you can see the health of

Last message received, unmatched messages, last error, last sync — on a screen, not in a log file. Most of the medium findings are only expensive because nobody can see them happening (F-10).

Recommendation

What to do, in what order

Ordered by risk removed per unit of work, not by severity label. The first two are small changes with disproportionate effect.

Order Work Removes Size
1 Close the webhook: verify the sender, and re-fetch the order from the Foodics API before writing anything from it. F-02, and most of F-08 Small

Worth saying plainly

Items 1 and 2 are each a few lines of code and together they remove the two ways a bill can be marked paid without anyone paying. If only one thing gets done from this document, it should be those two.

Method

How this review was done, and what it does not cover

What was read

The integration and everything it touches

All twelve integration source files, plus the payment engine, the QR scan endpoint, the table service, the database schema, the configuration layer, and the corresponding screens in the merchant panel and the guest app. Each finding was traced from the entry point a user reaches to the line that does the damage.

What was verified

Behaviour, not assumption

Claims that depend on framework behaviour were checked against the code rather than from memory: the transaction defaults come from the database service having no options set; the capture-before-record ordering from the payment intent being created without manual capture; the exposed payload from the app registering no serializer.

What was not done

Nothing was run

This is a reading of the code, not a live test against a Foodics account. Timing-dependent findings are argued from the code paths and are stated as reachable, not as observed in production. Reproducing F-01 and F-03 against a sandbox is the natural next step.

What is out of scope

The rest of the platform

Findings are limited to the Foodics integration and the code it changes the behaviour of. Where a problem is broader than Foodics — the absence of any refund path in the payments service, for instance — it is named as such rather than filed as a Foodics defect.
