01 · Ek nazar mein

Core mazboot hai, gadbad kinaron par hai — aur ek purana bug production mein hai

Payment ka sabse nazuk hissa — “paisa sach mein aaya ya nahi, aur ek payment ek hi baar record ho” — Fazal ne dhyan se banaya hai. Server browser par bharosa nahi karta, har baar AFS se khud puchta hai, aur double-record rokne ke kai taale lagaye hain. Jo problems mili hain woh zyada-tar aas-paas ki hain: secrets ka response mein chale jana, galat permissions, Stripe ka platform account, chupchap na jane wala webhook, aur release ki safety.

02 · Yeh system hai kya

Stripe Checkout jaisa, par hamare AFS ke saath

Abhi tak Smooth sirf apni jagah par payment leta tha: restaurant ka QR, payment link, customer app. Yeh naya system kisi bhi merchant ki apni website par payment lene deta hai — jaise ek perfume shop shop.example.com. Customer shop ki site par hi card / Apple Pay / Google Pay se pay karta hai, paisa merchant ke AFS account mein jata hai, aur shop ke server ko Smooth batata hai ki “order paid ho gaya”.

Ek misaal

Ayesha shop.example.com par 250 AED ka perfume cart mein daalti hai aur “Pay” dabati hai. Shop ka server chupke se Smooth ko bolta hai: “250.00 AED ka session banao, order-123 ke liye”. Smooth ek session id aur ek chhota password (client secret) deta hai. Shop ka page smooth.js load karta hai, jo Apple Pay / Google Pay / Card ka option dikhata hai. Ayesha card daalti hai — card ka data seedha AFS ke paas jata hai, Smooth ya shop tak nahi. Payment ke baad Ayesha shop ke “thank you” page par aati hai, jo Smooth se puchta rehta hai “paid hua?”. Smooth AFS se confirm karke ek Transaction likhta hai aur shop ke server ko signed message bhejta hai. Shop order bhej deti hai.

04 · Session ki zindagi

Paanch status, aur teen jaan-boojh kar rakhe gaye apvaad

StatusMatlabKaise pahunchta hai
CREATEDSession bana, page ne abhi kholna shuru nahi kiyaServer key se create
PROCESSINGPage khula / AFS checkout ban gaya, payment ka intezaarinit ya checkout
PAIDAFS ne success diya, amount match, Transaction likha gayaSirf AFS re-query se (webhook body se kabhi nahi)
FAILEDAFS ne saaf decline diya (issuer / risk / validation), ya admin ne hold ko failed kiyasettle ya admin

Apvaad 1

EXPIRED → PAID

AFS ka checkout id apne banne se ~30 min jeeta hai. Agar AFS checkout session ke 29ve minute par bana, to widget ~59 minute tak pay ho sakta hai. Session 30 par EXPIRED dikhega, phir payment aate hi PAID. Merchant ko yeh case sambhalna padega (order bhejo ya refund karo).

Apvaad 2

FAILED → PAID (sirf AFS, 2 ghante)

Card decline hua, page ne FAILED dikha diya, par Ayesha ne browser ka back dabaya aur usi AFS checkout par dusra card daal diya. COPYandPAY isko allow karta hai. Isliye 2 ghante tak FAILED session ko bhi dobara check kiya jata hai, aur sirf success mile tabhi PAID.

Apvaad 3

Hold

Jab AFS kuch aisa bole jisse paisa kat gaya ho par success code na ho (ya amount alag ho), status wahin ruk jata hai aur holdReason lag jata hai. Admin decide karta hai — section 06.

05 · Paisa kaise record hota hai

settle() — poore system ka dil

File: settle/settle-checkout.service.ts. Yeh function webhook, status poll, confirm, sweep aur admin recheck — sab se chalta hai. Iska kaam: AFS se sach puchna aur zyada se zyada ek Transaction likhna.

Kadam 1

AFS se dobara puchna

GET /v1/checkouts/{id}/payment. Agar AFS bole id expire ho gaya (200.300.404), to GET /v1/query?merchantTransactionId=… se dhoondhta hai — isiliye session par afsMerchantTransactionId save hota hai.

Kadam 2

AFS code ko 4 dibbon mein

paid: 000.000.*, 000.100.1* · pending: 000.200, 000.400, 800.400.5, 100.400.500 · unknown (kabhi decline nahi): 800.5/800.6/800.800.4/8, 600.1, 900.*, 999.* · declined: baaki 100.*/800.*. Cut-off (800.800.* + acquirer ne authorize kiya) → hold.

Kadam 3

Teen cheezein match

AFS ka reference = session par save reference; amount 2 decimal mein exact same (fils mein, float nahi); currency same. Kuch bhi alag → hold (paid nahi).

Kadam 4

Ek DB transaction mein dono kaam

Transaction row banao aur session ko PAID karo (sirf agar abhi bhi open ho). Ek fail to dono rollback. Do request ek saath aayi to unique key ki wajah se dusri pehli wali row “adopt” kar leti hai — double row nahi banti.

07 · Reconcile sweep

Har 2 minute ek chowkidaar ghoomta hai

File: settle/checkout-reconcile.service.ts. API ke har process mein setInterval. Koi lock nahi — jaan-boojh kar: settle dobara chalne par kuch nahi bigaadta, do instance hone par bas AFS ko ek extra call. Dhyan dein: dine-in AFS ke liye aisa sweep abhi bhi nahi hai (ISSUE-089, CRITICAL) — checkout mein Fazal ne bana diya.

13 · Kya gadbad hai

14 findings, sabse gambhir pehle

Har ek docs/KNOWN-ISSUES.md mein usi ID se likha hai. Maine koi code nahi badla — sirf report kiya. Har finding mein: kya hota hai, kab problem karega aur kab nahi, fix ki disha, aur exact file:line.

HighISSUE-104Production mein liveCheckout se alag

Admin Transaction Report se saare subscription payments gayab ho jaate hain

2 Oct ko Fazal ne admin report ko “sirf gateway wale payments” dikhane ke liye filter lagaya: jinki idempotencyKey foodics-pos: se shuru ho, unhe hatao. SQL mein jis row ki key khali (NULL) hai, woh bhi isi filter se hat jaati hai.

Kya hota hai

Prisma yeh SQL banata hai: NOT "idempotencyKey" LIKE 'foodics-pos:%' (maine query log mein dekha). SQL ka niyam: NULL ke saath har comparison ka jawab “pata nahi” hota hai, aur WHERE sirf “haan” wali rows rakhta hai. Membership / subscription ke transactions bina idempotencyKey ke likhe jaate hain — isliye woh report ki list, totals aur Excel teeno se gayab. Report mein “Subscription” filter hai par usme kabhi kuch nahi aayega. Merchant list ka “last transaction” bhi inhe ignore karta hai.

Kab problem, kab nahi

14 · Kya achha bana hai

Imaandari se: yeh hisse kaafi mazboot hain

Review sirf galti dhoondhna nahi hai. Neeche wali cheezein sahi hain aur inhe badalna nahi chahiye.

Paisa
  • Browser amount nahi badal sakta; PAID sirf AFS ke re-query se.
  • Ek AFS checkout = zyada se zyada ek Transaction: unique keys + DB transaction + guarded update; race par “adopt”.
  • Amount ka match canonical 2-decimal string mein — float nahi.
  • Dine-in ke saath takraav band: checkout ka AFS id dine-in confirm mein use nahi ho sakta, dine-in status mein dikhta nahi.
AFS ki samajh
  • Cut-off (800.800.* + acquirer authorized) ko decline nahi maana — dine-in ka hi rule, par yahan admin hold.
  • 900.* / 999.* / system errors kabhi decline nahi.
  • AFS id expire hone par /v1/query se dhoondhna (merchantTransactionId save karke).
  • Decline ke baad usi checkout par retry ko 2 ghante tak pakadna.
  • paymentBrand pre-set nahi; brands / wallet options live customer app jaise.
Bharosa aur suraksha
  • Reconcile sweep — jo dine-in mein abhi nahi hai.
  • Server key sirf hash, rotate par turant band; webhook secret encrypted.
  • Webhook SSRF protection (DNS pinning, private IP, redirect band).
  • smooth.js versioning + SRI; integrity bina live widget load nahi.
  • Rate limits Redis par (sab instance share karte hain).
Kaam ka dhang
  • 83 tests (26 spec files), har migration ka rollback SQL, module README.
  • Admin hold resolve par audit: kisne, kab, kyon (note zaroori).
  • Merchant ko PCI (SAQ A-EP) aur CSP ki saaf salah.
  • Geidea merge saaf — checkout Geidea merchant ko seedha mana karta hai.
