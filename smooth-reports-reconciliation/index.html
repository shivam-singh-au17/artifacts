The problem

What could not be answered before

Until now an admin could see one merchant’s transactions at a time, by opening that merchant’s profile. There were no filters and no export. So a perfectly ordinary question — “how much did we take across all merchants last month through payment links?” — had no answer short of opening every merchant in turn and adding it up by hand.

And when AFS sends the monthly revenue-share report, there was no way to check it. The report is a spreadsheet of card settlements; Smooth has its own record of every payment it took. Nobody had ever put the two side by side. If AFS under-reported a day, or Smooth failed to record a payment a customer was charged for, nothing would have caught it.

A distinction worth knowing about

When Smooth onboards a merchant with AFS, a small card charge is raised through the platform to get the account approved. That is a real payment and it appears in AFS’s settlement, so it has to be in the report — but it is not the merchant trading. It is flagged on every row and there is a filter for it, so a monthly revenue figure never quietly includes it.

Deliberate limit

A single export is capped at 100,000 rows. Past that the file becomes something no spreadsheet opens comfortably, so the report asks you to narrow the period instead of handing over something unusable.

02
Reports → AFS Reconciliation

Checking the AFS report

Upload the revenue-share spreadsheet AFS sends. The screen tells you what agrees, what does not, and what it could not judge either way.

01 Upload Drag the AFS file in. Nothing is saved — the result is held for an hour so you can read it and download it, then it is gone.
02 It reads every row Any row it cannot read is listed with the reason. Nothing is skipped quietly.
03 It pairs up payments Each AFS row is matched to the Smooth payment it belongs to, by merchant, amount and time.
04 You get the findings Six categories, worst first, with the one number that matters at the top: the difference between the two totals.

Three things you should know about how the match works

The reconciliation is careful, but it is working around a gap. None of this is hidden inside the software — it is printed on the screen and in the exported file, every run.

1. There is no shared reference number

Needs AFS

AFS identifies every row in the report by its own reference numbers — a retrieval reference, a merchant id, a terminal id. Smooth does not store any of them, so there is no shared key to join the two sides on.

What we do instead

Pair each AFS row to a Smooth payment by merchant, exact amount, and time. It is careful and it works, but it is inference rather than a lookup.

The fix, and what it needs

AFS does send us a reference on every single payment — Smooth simply never saved it. Storing it from now on makes every future reconciliation an exact lookup with no inference at all. We need AFS to confirm which reference will appear in the revenue-share report, then it is a small change.

Worth knowing

This only works going forward. Months already past can never be matched exactly, however the software changes.

2. The report covers far more than Smooth

Assumption

The AFS report is for the whole of Smooth Innovations Technology as a reseller — every merchant, and every card machine on their counters. In the sample month, 14,845 of 14,977 rows were physical card-machine takings that never touched Smooth. Only 132 were online payments at all.

The problem

No column in the report says “this row came from Smooth”. Comparing everything would report almost fifteen thousand “missing payments” — technically true, and completely useless.

What we do

A Smooth payment is always an online checkout, so only the online rows are reconciled. The card-machine rows are still summarised per account, so you can see them — they are just not treated as findings.

Confirm with AFS

If Smooth traffic can be identified some other way — a separate terminal id, say — tell us and we will use that instead. It is one line to change.

3. The report’s clock is unlabelled

Measured

The report prints a date and a time but never says which timezone they are in. Since matching depends on time, that matters. We read them as UAE time, which is what the pattern of the day in the sample suggests.

Why an assumption is acceptable here

Because the software does not just assume it — every run measures the actual gap it finds between the two sides and prints it next to the assumption.

What you will see

If the assumption holds, the summary says so. If the report is really on another clock, it says that too, with the exact offset it measured and a warning to confirm with AFS before acting on the findings.

Either way

A wrong guess cannot silently break the match. It shows up as a number on the screen.

Also stated on every run

Cash, cashback and Tabby payments cannot appear in an AFS report — cash never touches a card, and Tabby settles straight to the merchant. Rather than reporting all of them as missing, the summary counts them separately and says why they are out of scope. So the picture is complete without the noise.

Setup

Teaching it who is who

The AFS report names each merchant the way it is registered with the acquirer — the full legal trading name, legal suffixes and all. Smooth knows them by the shorter names they actually use. Those two rarely match exactly.

So the reconciliation resolves a merchant in two steps. First it looks for a recorded AFS merchant id. If there is none, it tries an exact name match after tidying both names up. If neither works, it says so instead of guessing — a wrong guess in a settlement report means putting one business’s money against another, and would never announce itself.

Every unmapped account appears in the report with a Map merchant button. Pick the right merchant once, and the id is recorded against them. From the next upload on, that account resolves on its own.

One-time, per merchant

Where the ids live

Also editable directly on the merchant, under Merchants → Payment → Settlement identifiers. Filling these in for each merchant is the single thing that makes reconciliation fully automatic.

Guard rail

One account, one merchant

An AFS merchant id can only be recorded against one Smooth merchant. Trying to give the same id to a second one is refused, with the name of the merchant already holding it — rather than quietly merging two businesses’ settlement figures.

Why the numbers can be trusted

Built so two figures cannot disagree

This is money. A report whose total does not match its own rows is worse than no report at all, so a few things were made impossible rather than merely tested.

The screen and the file

Are the same thing

The Excel export is not a second calculation of the report — it writes the identical values the screen received. There is no path by which the file could show a different figure.

Totals

Come from the database

Every total is computed by the database over the whole filtered set, not by adding up the page you are looking at. So a total always describes the report, never just the visible rows.

Amounts

Compare to the fils

Money is compared as whole fils, never as decimal fractions. Two payments that agree can never read as a discrepancy because of a rounding artefact.

Filters

Are defined once

The list, the totals and the export all ask the same question of the database. A count that disagreed with the rows behind it is not something that can happen.

The uploaded file

Loses nothing silently

Any row that cannot be read is reported with its row number and the reason. An amount with more precision than a fils is rejected rather than rounded — quietly changing money is not an option.

The matching itself

Is tested and repeatable

Twenty-one automated checks cover the awkward cases: repeated identical amounts, a wrong timezone, an extra row on one side, two merchants with the same figures at the same moment. The same file always produces the same result.
