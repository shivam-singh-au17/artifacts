1.1 Why one service, and the conditions under which we would split it

Recorded here rather than only in the planning notes, because whoever builds this will eventually be asked the question and should not have to reconstruct the answer.

The argument that actually decides it

When the gateway confirms a payment, three rows have to be written in one database transaction: the attempt becomes succeeded, the intent becomes succeeded with its captured amount, and the outbound event is created. Keeping those three together makes two states structurally impossible: a payment recorded with no notification queued, and a notification sent for a payment that was rolled back. Split the event into another service and that transaction has to be replaced with an outbox or a compensating saga. That is buildable, but it is precisely the place where money goes missing, and there is no benefit here to pay for it.

So the rule is narrower and more useful than "monolith rather than microservices": the payment core, meaning intent, attempt and outbound event, lives in one service. Everything around it could be split, and there is currently no reason to.

1.2 The modules, and the boundaries the build enforces

The real risk of this choice, stated plainly

A modular monolith fails by erosion, not by design. Boundaries that exist only as a convention get crossed under deadline pressure, one import at a time, and in eight months the result is indistinguishable from the 4,312-line service this product was meant to improve on. The boundaries below are therefore enforced by the build, not by code review. A forbidden import fails continuous integration in the same way a type error does.

If a gateway field name reaches a controller, a response or a merchant, then changing gateway is no longer free, and the reason for building this service has quietly evaporated
interfaces/ may not import infrastructure/providers/ directly Dependency rules Forces every gateway interaction through the orchestrator, so there is no side door that skips idempotency, the amount assertion or the audit trail

Without this check it is a sentence in a document that a job or a controller will eventually ignore
infrastructure/providers/ may not import persistence/ Dependency rules Adapters stay pure translators: a domain command in, a domain result or a typed error out. An adapter that can reach the database will grow business rules inside it
No module may import another module's internals, only its entry point Dependency rules Keeps each boundary small enough that lifting a module out later is a contained piece of work rather than an archaeology exercise
No raw provider response object may be passed to a logger, and no any may cross a module boundary Lint rule plus the grep already described in §12 One of these is a compliance control and the other is how a weakly typed value becomes a runtime surprise in a money path
How this is set up

A dependency rules configuration committed in the repository, run in continuous integration alongside the type check, plus two or three narrow lint rules for the write-path and logging restrictions. It is roughly half a day to set up in week one, and it is the cheapest architectural insurance available on this project.

What it is not

It is not a style preference and it is not there to slow anybody down. Every rule above maps to a specific failure: an untestable domain, a leaked gateway, a bypassed idempotency check, a second writer, a business rule buried in an adapter, or a card field in a log.

The test of whether it worked

Adding the second gateway in a later phase should require one new directory under providers/, a capability declaration and a set of fixtures, and no change to the domain, the API, or any caller. If that turns out not to be true, the boundaries were not enforced, and this section is where to look first.

2.1 Our answer to each, and how the unknown is isolated

A question list on its own transfers the problem rather than solving it, and most of these cannot reasonably be answered by whoever is asked. So each one below carries our recommendation, the reasoning a reviewer can argue with, and what we build so that a late answer costs nothing. That last column is the important one: it is how nine of the ten stop being blockers.

#RecommendationReasoningHow the unknown is isolated
B1 One merchant, many applications. Not a merchant per website Both shapes can bind a gateway per website, so capability does not decide it. The asymmetry of being wrong does. Choosing a merchant per website and later needing to group them means re-parenting live financial rows, which is a migration nobody wants to perform on real money. Choosing the extra level and never needing it costs an auto-created row and a selector the panel hides when a merchant has one application. There is also a product consequence: separate merchants cannot share a login, a dashboard, an invoice or a combined figure, and a business with a main site and an outlet will ask for all four It is not. This is the one genuine blocker. Six tables and every tenancy check derive from it, and no amount of design can defer it. It needs a yes or a correction, not research
B2 Build a simulated provider and make the test suite depend on it, not on the gateway's sandbox. Assume amount-driven results until told otherwise The existing platform carries a helper that rewrites a charge to whole units on the sandbox, double-gated on test mode, which is strong evidence the sandbox reads the minor units as a result selector. That is a guess, though, and a test suite built on a guess proves nothing. A simulator we control can be told to succeed, decline, require a challenge, return no result code, or go silent, which is more than any sandbox will do for us anyway The gateway port already exists as an interface. A second implementation of it, backed by fixtures, is roughly two days and makes the automated suite run in seconds, offline, deterministically. The real sandbox is then used only for the manual smoke test, and the printed card list on one merchant screen is the only thing still waiting
B3 Build the longer path: issue the association file, the merchant hosts it, we fetch it to verify, then register. Apple validates the file on the domain hosting the payment page, and for an embedded box that is the merchant's domain, not ours. So the hosting step exists under every possible answer. If the gateway can register domains on our behalf through Apple's provider interface, our screen collapses to one button and the work already done still applies. Designing for that easier case first would mean rebuilding the screen if the answer goes the other way The registration call sits behind one function with two implementations, selected by configuration: we call the gateway's registration endpoint, or an operator completes it and marks it done from the admin panel. Verification, state machine, daily re-check and the button-hiding rule are identical either way
B4 Ask, but plan the acceptance test as one small live payment on our own account. Sandboxes commonly lack wallet support, and discovering that in the week the wallets are due would move the date. The platform already performs a low-value live transaction as part of gateway approval, so both the practice and the precedent exist Wallet work is scheduled deliberately late. Until then the simulator covers the wallet code paths, and the device test is a manual step on a real account for a trivial amount, documented as such rather than pretended to be a sandbox test
B5 Assume one notification address serves both modes, and resolve mode and tenant from the message itself. Our attempt reference is deterministic and derived from the intent, and the intent carries the application and the mode. So an incoming message that echoes our reference tells us everything we need without the gateway keeping environments apart on our behalf. If it turns out separate addresses are possible, we use them as a second layer rather than as a dependency. This also avoids the failure the current platform has, where per-entity notification addresses point at the wrong endpoint and messages are dropped while we answer 200 Fully isolated. The inbound handler never reads a mode or a tenant from configuration. A message whose reference cannot be parsed is stored, flagged as unmatched and surfaced, never discarded
B6 Do not wait for the answer. Support both shapes unconditionally. Read the body as text, decrypt when the two encryption headers are present, parse as plain otherwise. The billing rail already contains a working implementation of exactly this, so it is a port rather than new work. A confident answer today could also change later per entity, whereas handling both is permanently correct Fully isolated, for roughly half a day. This is the clearest case on the list where handling both beats knowing which
B7 Impose our own budget rather than discovering theirs. A token bucket per provider account, plus automatic backoff on any 429 or 5xx The sweeper is the component that could hammer the gateway, and it runs hardest at exactly the wrong moment, during an incident when many attempts are unresolved. A self-imposed ceiling means an unknown limit cannot hurt us, and a discovered limit is a configuration change rather than a redesign Fully isolated. Starting values: a small number of queries per second per account and a bounded concurrency overall, both in configuration. Any 429 halves the rate for a cooling period and the sweeper reschedules rather than retrying immediately
B8 Merchant-owned accounts only in Phase 1, and the platform-owned value blocked in code. It is the confirmed position, it needs no licence, and the whole design already assumes it. The stronger half of this recommendation is the guard: the column accepts PLATFORM so the future model needs no migration, and a startup assertion refuses to run with any such row until a licence flag is deliberately set. Making an unlicensed configuration impossible to enable by accident is worth one line Fully isolated. Nothing in Phase 1 reads the value except that guard
B9 1800 seconds, configurable per application between 300 and 3600. Below roughly fifteen minutes and genuine sales are lost to a shopper fetching a card or waiting on a slow bank code. Above an hour and a merchant holds stock against a payment that will not arrive, while stale pages accumulate. Thirty minutes covers a challenge comfortably and matches common practice. It is also a low-risk number because expiry gates initiation and never evidence: a late confirmed capture still settles, so a shorter window costs conversion rather than money Fully isolated. One default and one per-application override, both already in the schema
B10 No shopper email at all. The merchant sends the receipt. The shopper transacted with the merchant, and a message from an unfamiliar sender produces support load on both sides and at worst is reported as phishing. The merchant also holds the order contents; we hold an amount. There is a further reason to prefer this: an email to a shopper makes us a party they will contact about a purchase we know nothing about. If a merchant later wants us to send it, the right shape is a template sent under their name with their reply address, which is a Phase 2 feature rather than a Phase 1 module Fully isolated, and it removes a module, a template set and a deliverability concern from Phase 1. No shopper address exists in any template and no code path could send to one
What this section is really for

Two things. First, whoever has to answer these should not need to understand a payment gateway to do it: they read a recommendation and either agree or correct it. Second, and more important for the schedule, nine of the ten are structured so that a late answer changes a configuration value or switches one function implementation, never a design. Only B1 is a real gate, because tenancy cannot be deferred behind an interface.

The discipline this replaces

The alternative to this section is the pattern that produced the problems recorded against the current platform: an unknown gets a plausible assumption, the assumption gets built on, and a customer discovers it eighteen months later. Every row above either states an answer we are prepared to defend, or names the single function behind which the unknown is confined. There is no third category, and no row is left as "we will find out during development".

4.1 Three decisions inside this model

Why intent and attempt are separate

In Smooth Pay today the ledger row is created only on success, so a decline leaves no record and per-attempt state lives in a shared JSON column on the order. That column is overwritten when two people pay the same bill at once, which is recorded there as a known issue.

Splitting them fixes that class of problem before it exists here, makes declines measurable, and gives a retry somewhere to live.

Why there is no separate session table

Decision The earlier checkout plan proposed a session object between the intent and the browser. Here the intent carries the client_secret and the expiry directly, and each browser initialisation creates an attempt.

One fewer object, one fewer API call for the integrator, and the same guarantees. It matches how Stripe exposes a PaymentIntent, which is the model the client asked us to learn from. If several concurrent browser handles per intent are ever needed, a session table is additive.

Why the provider account is locked on the attempt

Because a payment taken on one gateway can only be queried, reconciled and later refunded on that same gateway. Storing the binding on the attempt is what lets us move a website to a new gateway at any moment without waiting for a quiet hour and without stranding anything in flight.

The three lines that carry the design

provider_account hangs off the merchant, not the application. So one gateway account can serve several websites, and an application-level row overrides it when a website needs its own.

payment_attempt points at exactly one provider_account. That is the arrow marked above, and it is why a gateway switch is safe.

payment_intent hangs off the application. So tenancy, keys, domains and payments all resolve from the same parent, and a cross-tenant read has to break the same single join everywhere.

Where a query starts

Every merchant-facing read starts from an application_id derived from the key or the session. Every admin read starts from a merchant_id. No read ever starts from a payment id alone, which is what makes a guessed id useless rather than merely unlikely to be guessed.

Deletes

There are none on financial rows. Foreign keys are ON DELETE RESTRICT throughout. A business that leaves is suspended, and its records stay, because an acquirer settlement query can arrive months later and must still resolve.

The expiry exception, stated once

Expiry gates starting. Evidence gates money. A shopper who enters a bank challenge at minute 29 and finishes at minute 31 has been charged. An expired intent must refuse new attempts and must still accept a gateway-confirmed capture. The alternative is money taken and never recorded, which is the worst state a payment system can be in. This is the only transition in the product that moves backwards, and it exists for that reason alone.

Unknown is not failure

A timeout, a 5xx with no body, or a body with no result code means we do not know. Those become or remain processing and the recovery job owns them. Mapping unknown to failed is how a charged customer is told their payment failed, and then pays twice.

6.4 How a held payment is resolved

A hold is the only state that requires a human, so its exit has to be specified rather than improvised.

StepWhoWhat happens
Hold createdThe serviceThe attempt and the intent both become held. No money is recorded and no event is emitted to the merchant. A payment.held event is created but withheld from delivery until a decision is made, so nothing is lost if the process restarts. Our team is alerted at once.
InvestigationOwner roleThe admin screen shows what we asked for beside what the gateway reported, plus every raw message received. The gateway can be re-queried from the screen, which resolves most holds on its own.
AcceptOwner roleRequires a written reason. Settles at the amount the gateway actually reported, never at the amount we asked for, because the reported figure is the money that moved. Validation, in order

Key is valid and not revoked, application is not suspended, idempotency key present and consistent, amount is a positive integer number of fils once parsed, currency is AED, return and cancel URLs are HTTPS and on an allowed domain, metadata within limits, and an active provider account exists for this application and mode. Any failure is a 4xx to the merchant's server, never a broken box in front of a shopper.

What is deliberately absent

No gateway name, no entity identifier, no merchant id in the body. The tenant comes from the key and only from the key. A body field claiming a different merchant is rejected outright rather than merged.

Amount as a string

Decision Decimal strings in and out, integer fils inside. Every language parses "240.00" identically; not every language parses a JSON number identically. This is the cheapest way to make a whole class of integration bug impossible.

TimesISO 8601 with a Z suffix, always UTC, always to milliseconds. The panels convert to UAE time for display; the API never does. A report that spans a month must not depend on whose clock rendered it.

VersioningThe path carries /v1/. Payload shapes are pinned per application by a dated api_version. Fields are only ever added, never removed or repurposed. A merchant moves to a newer version deliberately, from their own panel, and can move back for 30 days.

Request idEvery response carries Smooth-Request-Id. It appears in every error body and in every log line for that request. Support asks for this one value and nothing else.
CompatibilityA new payment method, a new gateway or a new status value must not change any existing response shape. This is asserted by snapshot tests, and a deliberate break requires a new api_version.

8.8 The status channel, and the route the gateway returns to

Two mechanisms that together cover the shopper who stays and the shopper who leaves.

MechanismWhat it isBehaviour
Live status Server-sent events on GET /v1/checkout/:id/stream, with polling on /status as the fallback Events are chosen over a socket because the traffic is one-directional and short-lived, and because server-sent events survive corporate proxies that break websockets. The fallback is not optional: any client that cannot hold the stream open polls at no faster than the configured floor. Both paths re-query the gateway when the attempt is still open, so neither can report a stale state. The stream closes on a terminal status or at the intent's expiry, whichever comes first.
Return route GET /r/:attemptId on the payment page origin This is the URL handed to the gateway, and it is where the browser lands after a bank challenge. It is a real page, not a redirect: it re-opens the payment page in the state the attempt is actually in. If the challenge happened in the top window it also restores the frame and tells the parent page. It accepts no query parameter that could influence a decision, because whatever the gateway appends is attacker-influenced; the attempt id in the path is the only input, and the outcome still comes from asking the gateway.
Why neither of these settles anything

The stream reports state, the return route restores a screen. Neither writes payment state. Settlement happens in exactly one place, the transaction in §10.1, reached only from a gateway status response. A shopper who never loads the return route at all, because they closed the tab, changes nothing about whether the payment is recorded.

Why always 200

A 4xx or 5xx makes the gateway retry, and sustained failures can get an endpoint disabled at their end. This is already the rule in Smooth Pay's production handlers and it is carried over unchanged. Verified

Why text, not JSON

Because an encrypted notification arrives as a hex string. Smooth Pay's dine-in endpoint parses JSON and therefore silently drops those, which is recorded there as a known issue. This service reads text first and decides afterwards.

One code path for every gateway, whatever its signature strength. A forged message then costs us one query and settles nothing. It also means the day a second gateway arrives with weaker signing, no new trust model is needed.

9.3 Outbound egress rules

A merchant's notification URL is attacker-influenced input and is treated as such.

  • HTTPS only. No plain HTTP, in any mode, including test.
  • DNS is resolved by us, and the resolved address is rejected if it is private, loopback, link-local, or the cloud metadata address.
  • The connection is made to the resolved address, not re-resolved by the HTTP client. Without this, a hostname that resolves to a public address during the check and a private one a moment later would defeat the check entirely. This is the detail most implementations of this rule miss.
  • No redirects are followed, at all.
  • Response body read is capped at 64 KB, and the connection has a hard timeout.
  • Requests leave through a dedicated egress path with no access to internal services.

Four layers, each answering a different question

All four are database constraints. None of them is application logic that could be bypassed by a second copy of the service running at the same moment.

3Has this gateway payment already landed?UNIQUE(provider, provider_payment_id) and UNIQUE(provider, provider_ref)The second writer gets a unique violation and returns the first result. This is what makes a notification racing a browser confirmation harmless

10.1 The settlement transaction

The only place in the service that requires a serialisable transaction 
BEGIN ISOLATION LEVEL SERIALIZABLE
  SELECT ... FROM payment_intent WHERE id = $1 FOR UPDATE
  re-read the attempt; if already terminal, return the existing result
  assert:  reported_amount == amount  AND  reported_currency == currency
           AND the gateway echoed our attempt_reference
  on any assertion failure → status held, write no money, emit no event
  UPDATE payment_attempt  SET status='succeeded', settled_at=now(), …
  UPDATE payment_intent   SET status='succeeded', amount_captured_minor=…
  INSERT outbound_event   (dedupe_key = intent_id || ':succeeded')   ON CONFLICT DO NOTHING
COMMIT
then, outside the transaction: enqueue delivery
  • The event row is written inside the transaction so an event can never exist for a payment that was rolled back, and a payment can never be recorded without its event being queued.
  • The delivery attempt is made outside it, so a slow merchant server can never hold a database lock.
  • A serialisation failure is retried up to three times with jitter. That is the correct response, not an error.

Definition of done

The tests that decide whether Phase 1 ships

These are not a wish list. Phase 1 is finished when every one of them passes, and not before.

Money correctness
  • A confirmation arriving after expiry still settles, exactly once.
  • An amount mismatch writes no money, emits no event, and produces a held payment.
  • A currency mismatch does the same.
  • A replayed confirmation returns the original result through the unique-violation path.
  • The sweeper settles an attempt whose browser poll never returned.
  • An acquirer cut-off result settles rather than failing.
  • A gateway response with no result code leaves the attempt open, never failed.
Idempotency and concurrency
  • The same creation request twice produces one intent and two identical responses.
  • The same key with a different body returns 422.
  • An in-flight key returns 409.
  • Two tabs initialising at once produce one attempt.
  • A notification and a browser confirmation racing produce one settlement.
  • Two workers claiming one attempt produce one gateway call.
Security
  • A key from one application cannot read another's intent, at the API and at the repository.
  • Row-level security blocks a cross-tenant read even when the repository filter is deliberately removed in the test.
  • Initialising from a domain not on the list is refused.
  • A forged notification settles nothing.
  • A notification URL resolving to a private or metadata address is refused at send time.
  • A hostname that resolves publicly then privately is still refused.
  • No raw gateway body reaches a logger, asserted by a build-time check.
  • A client secret cannot be brute forced within the rate limit.
Gateway adapter
  • Recorded real responses used as fixtures: success, decline, pending, cut-off, parameter conflict, nothing-to-reverse, result-code-on-4xx, and an unreadable body.
  • The mapper never lets a gateway field name or code escape the adapter, asserted by a test that inspects the serialised output.
  • Reference build and parse round-trip for every attempt number up to 99.
End to end, against the sandbox
  • Card payment, success and decline.
  • Bank challenge, completed and abandoned.
  • Apple Pay on a real device, once B3 and B4 are answered.
  • Google Pay on a real device.
  • The box on a real third-party page, including the permission attribute.
  • An unverified domain hides the Apple Pay button and the card path still works.
The human tests
  • Someone outside the team integrates from the documentation alone, with no help, and takes a test payment.
  • A support person answers "what happened to this payment" using only the admin panel.
  • A gateway switch is performed on a test merchant with payments in flight, and none of them is lost.

Build order

Ordered so that the riskiest unknown is met early and the work that depends on an outside answer sits late.

Honest note on the estimate

The earlier plan said six to eight weeks. Two things have been added since: the wallets, and sign-in with roles and invitations for two panels, which a brand new product cannot inherit from anywhere. Seven to nine weeks with two backend and one frontend developer working full time is the realistic figure, and it assumes the gateway answers B2 within the first fortnight. If that answer is late, the testing work moves and the date moves with it.
